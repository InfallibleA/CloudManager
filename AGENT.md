## 1. Обзор проекта

**CloudManager** — сервис облачного хранилища и управления контентом, включающий в себя бэкенд на FastAPI, интеграцию с объектным S3-хранилищем (Garage), поддержку клиентских приложений (Desktop Client) и витрины новостей/медиа.

### Архитектура и стек технологий:
* **Язык**: Python 3.14
* **Пакетный менеджер**: `uv` (`pyproject.toml`, `uv.lock`)
* **Фреймворк**: FastAPI + Uvicorn
* **База данных**: PostgreSQL 17, SQLAlchemy 2.0 (asyncio) + asyncpg, миграции Alembic
* **Хранилище объектов**: Garage (S3-совместимое хранилище) + presigned-ссылки
* **Внедрение зависимостей (DI)**: Dishka (`dishka.integrations.fastapi`)
* **Конфигурация**: `pydantic-settings` (`app/config.py`)
* **Аутентификация и безопасность**: JWT (`pyjwt`), хеширование паролей (`bcrypt`), ролевая модель (клиенты, администраторы, блокировка пользователей)
* **Качество кода и тесты**: pytest (`pytest-asyncio`), Ruff (линтер и форматтер), pre-commit
* **Инфраструктура**: Docker Compose (сервисы `postgres`, `garage`, `migrate`, `api`, `nginx`)

### Основные модули приложения (`app/`):
* `audios/` — загрузка, переименование, удаление аудио, справочник форматов и воспроизведение через presigned URL (только для авторизованных пользователей).
* `auth/` — регистрация, аутентификация, выдача токенов, управление пользователями (блокировка/разблокировка).
* `users/` — модель пользователя, репозиторий, CLI-утилиты (`create-admin`).
* `files/` — загрузка файлов в S3 (Garage), генерация presigned-ссылок для скачивания/просмотра, inline images, мягкое удаление.
* `folders/` — персональные папки пользователей с поддержкой иерархии (вложенности), привязкой файлов, видео и аудио и каскадным удалением связанных элементов.
* `videos/` — загрузка видео, справочник форматов, стриминг/плейбек через presigned URL.
* `news/` — новостной раздел витрины с прикреплёнными медиафайлами и приоритизацией (весами).
* `health/` — проверки работоспособности (`/health` для liveness, `/health/ready` для готовности БД).
* `core/` — базовые модели (`Base`, `SoftDel`), базовые репозитории, транзакции БД, CORS, глобальная обработка исключений.

### Документация (`/docs`):
* `docs/api.md` — актуальная спецификация существующего HTTP API сервиса (подлежит обязательному обновлению при любых изменениях API).

## 2. Команды для запуска, тестирования и линтинга

Все команды выполняются из корня проекта.

### 2.1. Установка окружения и зависимости
```bash
# Установка зависимостей и создание .venv через uv
uv sync
```

### 2.2. Запуск тестов (pytest)
```bash
# Запуск всех тестов
uv run pytest

# Запуск с подробным выводом
uv run pytest -v

# Запуск конкретного тестового файла
uv run pytest tests/test_<name>.py

# Запуск конкретного теста по названию
uv run pytest -k "test_function_name"
```

### 2.3. Линтинг и форматирование кода (Ruff)
```bash
# Проверка и авто-исправление линтером
uv run ruff check --fix .

# Форматирование кода по стандартам проекта
uv run ruff format .
```

### 2.4. База данных и миграции (Alembic)
```bash
# Применение всех миграций
uv run alembic upgrade head

# Создание новой миграции с автогенерацией
uv run alembic revision --autogenerate -m "описание изменений"

# Откат на одну миграцию назад
uv run alembic downgrade -1
```

### 2.5. Локальный запуск приложения
```bash
# Запуск через Uvicorn в режиме автоперезагрузки (reload)
uv run uvicorn app.main:app --reload

# Создание учётной записи администратора через CLI
uv run python -m app.users.cli create-admin
```

### 2.6. Docker Compose
```bash
# Сборка и запуск ключевых сервисов в фоне
docker compose up -d postgres garage migrate api nginx

# Применение миграций внутри запущенного контейнера
docker compose exec api alembic upgrade head

# Запуск тестов внутри контейнера
docker compose exec api pytest

# Просмотр логов API
docker compose logs -f api
```

## 3. Правила и процессы GIT

> [!IMPORTANT]
> **СТРОГИЙ ЗАПРЕТ НА САМОСТОЯТЕЛЬНЫЕ ДЕЙСТВИЯ В GIT!**
> Агенту категорически запрещено выполнять модифицирующие git-операции без явного одобрения пользователя.

### Запрещено выполнять самостоятельно:
* ❌ **НЕ ПУШИТЬ** (`git push`) — никогда не отправлять изменения в удалённый репозиторий без прямого запроса.
* ❌ **НЕ СОЗДАВАТЬ КОММИТЫ** (`git commit`) — не фиксировать изменения самостоятельно.
* ❌ **НЕ СЛИВАТЬ ВЕТКИ** (`git merge`, `git rebase`) — не объединять ветки без команды пользователя.
* ❌ **НЕ ПУЛЛИТЬ** (`git pull`, `git fetch` с автослиянием) — не подтягивать и не применять внешние изменения без разрешения.

### Обязательный протокол согласования:
1. **Проверка состояния**: перед предложением коммита или ветвления запустить `git status` и `git diff --stat`.
2. **Формирование запроса**:
   * Описать пользователю суть подготовленных изменений.
   * Предложить понятное и лаконичное сообщение коммита (Conventional Commits, на русском или английском по контексту).
   * Указать конкретную команду (например, `git commit -m "..."` или `git push origin <branch>`).
3. **Ожидание подтверждения**: выполнять команду **только** после того, как пользователь явно даст согласие (например, «делай коммит», «пушь», «да»).

## 4. Принципы разработки (ub-mode)

При любых изменениях в кодовой базе придерживаться трёх фаз:
1. **First Make it Work**:
   * Минимальный рабочий объём (Ship the smallest edit that solves the problem).
   * Выверенная модель данных и строгая типизация до написания сложной логики.
   * TDD: сначала падающий тест на ожидаемое поведение, затем минимальный код для прохождения теста.
   * Валидация на границах входа (Pydantic, валидаторы), доверие внутри доменной логики.
2. **Then Make it Right**:
   * Устранение первопричины багов, а не маскировка падений guard-проверками.
   * Тестирование внешнего поведения контрактов, а не деталей внутренней реализации.
   * Рефакторинг с гарантией неизменности контрактов.
3. **Follow Practice**:
   * Ведение журнала действий (Keep a Log) с обоснованием шагов и отчётом по завершении задачи.
   * Экономия контекста.
